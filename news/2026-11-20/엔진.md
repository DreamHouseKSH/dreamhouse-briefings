## 1. vLLM, AMD FlyDSL 'MonoKernel'로 디코드 지연 줄이기 — 커널 경계를 지우는 지속 실행

- **원문:** https://vllm.ai/blog/2026-11-18-flydsl-monokernels (vLLM 공식 블로그)
- **분야:** 엔진 · 추론 최적화
- **최초 게시:** vLLM 블로그 2026-11-18
- **시간 판정:** 정규 구간 내 확인

### 요약

vLLM 팀이 AMD Instinct GPU에서 인터랙티브 LLM 서빙의 디코드(decode) 지연을 줄이는 'MonoKernel' 접근을 공개했다. 배경: 코딩 에이전트처럼 다음 행동이 현재 생성에 의존하는 워크로드는 디코드가 치명 경로인데, 작은 배치에서는 각 GPU 커널의 디스패치·시작·종료 비용이 지연의 큰 부분을 차지한다. HIP 그래프는 CPU 실행 오버헤드만 줄일 뿐 이 GPU 측 비용은 못 없앤다.

MonoKernel은 의존 관계의 여러 연산 단계를 하나의 커널 실행 안에 넣되, 고정된 스레드블록 그리드가 단계를 넘나드는 지속(persistent) 실행으로 만든다. TileRT에서 영감을 받았고, ① 블록이 다음 단계의 준비된 작업을 이어받고 ② 이전 연산 중에 뒤 단계의 가중치를 미리 읽고 ③ 태그드 메일박스(tagged mailbox)로 소비자가 필요한 타일 단위에서 데이터를 넘겨받는다. 구현 언어는 AMD의 Python DSL/MLIR 컴파일러 FlyDSL이다. 경계는 모델별로 다르다: DeepSeek-V4.1-Flash(#60397)는 어텐션 앞부분(K1)과 어텐션 뒷부분+TP all-reduce+MoE(K2)의 두 경계로 나눴고, MiniMax-M3(#62712)는 FFN 부분만 융합했다. "어느 한 방식이 모든 모델에 옮겨가는 고정 레시피가 아니다"라고 명시했다.

### 논조·다른 시각

- **기사 논조:** 중립~긍정 — 설계 설명 중심의 기술 블로그며, 개략도가 '측정치가 아님'을 반복 명시한다.
- **논조 점검:** 성능·정확도 섹션은 본문 후반에 있고, 이 발췌 범위에서는 구체 수치 확인이 안 됐다. 모델·GPU 아키텍처·스텝 폭에 따라 실행 가능한 변형이 갈린다는 단서가 붙는다.
- **다른 시각:** 작성자가 설계하고 DSL이 컴파일하는 방식은 자동 융합보다 유연하지만, 모델마다 커널 경계를 새로 설계해야 한다는 엔지니어링 비용이 있다.

**시사점:** 추론 최적화의 전선이 '커널을 빠르게'에서 '커널 사이를 없애기'로 이동 중이다. AMD GPU에서의 이 작업은 엔비디아 중심 추론 스택의 대안 축을 키우는 시도이기도 하다.

## 2. llama.cpp — M5 텐서 코어 CONV_2D, 로더 보안 하드닝, 웹 UI 초기 로딩 63% 절감

- **원문:** https://ai-eng-digest.astgl.ai/sections/local.html (AI Engineering Digest 2026-11-19판, llama.cpp PR #32542·#32562·#32495·#32555 등)
- **분야:** 엔진 · 로컬 추론
- **최초 게시:** AI Engineering Digest 2026-11-19판 (머지 일시 11-18~19 ET)
- **시간 판정:** 정규 구간 내 확인

### 요약

llama.cpp에 18~19일(현지시간) 성능·보안·UI 개선이 잇달아 머지됐다. ① Metal CONV_2D(#32542): M5에서는 텐서 API로 합성곱을 행렬곱처럼 텐서 코어에서 돌리고, M1~M4는 기존 simdgroup 커널을 유지한다. 모든 칩에서 긴 리덕션을 스레드그룹 간 분할(split-K)하되 부분합을 고정 순서로 더해 결정성을 보장한다. 비전·오디오 인코더와 이미지 모델에 주로 해당한다. ② 모델 로딩 하드닝: 조작된 `limite` GGUF로 텐서 로드 중 고정 배열을 넘겨 읽을 수 있던 문제(ASan 확인)를 hparams 단계에서 거부(#32562), gguf-py GGUFReader의 uint64 오프셋 오버플로를 수정(#32495). 깃허브 권고문(advisory)은 없고 나이틀리에만 포함됐다. ③ 웹 UI(#32555): 첫 로드 JS가 gzip 기준 2.85MB에서 1.06MB로 줄고 다이어그램·수식·PDF 처리를 지연 로딩한다.

이 밖에 VoxCPM2 mtmd(#32443), Zyphra Zaya1 8B(#32071), recurrent state sticky-NaN 수정(#31913) 등이 머지됐다. 최신 나이틀리는 b12540(19일 08:01 ET), v1.0.0(11-13) 이후 태그 릴리스는 없다. Ollama는 안정판 0.40.16 유지다.

### 논조·다른 시각

- **기사 논조:** 중립 — PR 머지 사실 정리다.
- **논조 점검:** 보안 수정 2건에 권고문이 없다는 점은 나이틀리 사용자가 스스로 판단해야 한다는 뜻이다. 신뢰할 수 없는 GGUF를 받아 쓰는 환경이라면 이번 나이틀리 반영이 필요하다.
- **다른 시각:** M5 전용 텐서 경로는 애플 실리콘 세대별 최적화가 다시 갈라지기 시작했다는 신호다.

**시사점:** 로컬 추론 스택의 성숙은 신모델 지원 속도뿐 아니라 로더의 견고성으로 측정된다. GGUF가 배포 포맷으로 굳어질수록 포맷 파서의 공격 표면은 커진다.

## 3. NVIDIA RTX Spark 데스크톱 출시 — ASUS·Dell·MSI부터, "120B 모델 로컬 실행"

- **원문:** https://ai-eng-digest.astgl.ai/sections/local.html (AI Engineering Digest 2026-11-19판, NVIDIA 블로그 11-18 기준)
- **분야:** 엔진 · 로컬 하드웨어
- **최초 게시:** NVIDIA 블로그 2026-11-18 09:00 ET (다이제스트 11-19판 수록)
- **시간 판정:** 정규 구간 내 확인

### 요약

NVIDIA RTX Spark 기반 소형 데스크톱이 출시됐다. ASUS(ProArt GR1X), Dell, MSI(EdgeMesa N AI+) 제품이 구매 가능하고, Acer·기가바이트·HP 미니 PC와 Microsoft Surface RTX Spark Dev Box는 "곧" 나온다. 스펙은 20코어 Grace CPU, 6,144 CUDA 코어의 Blackwell RTX GPU, 최대 128GB 통합 메모리, "최대 1페타플롭 AI 성능", 10GbE이며 Windows on Arm에서 CUDA와 WSL을 지원한다. 소프트웨어는 Hermes Agent, NemoClaw 블루프린트, Unsloth 파인튜닝, ComfyUI가 언급됐고, 로컬/클라우드 라우팅 도구 NVIDIA Switchyard가 Hermes에 들어갔다.

NVIDIA의 주장(120B 파라미터 LLM 로컬 실행, 90GB 이상 3D 장면)은 회사 발표이며, 다이제스트는 가격과 토큰 속도가 공개되지 않았다고 지적했다. MS Ignite에서는 RTX Spark 탑재 Windows PC의 로컬 LLM 시연이 예고됐다(IT 브리핑 2번).

### 논조·다른 시각

- **기사 논조:** 중립 — 스펙 정리와 미공개 항목 표기다.
- **논조 점검:** '120B 로컬'은 양자화 수준과 컨텍스트 길이 조건이 빠진 마케팅 수치다. 가격·실측 처리량이 나오기 전에는 비교가 어렵다.
- **다른 시각:** Windows on Arm + CUDA 조합은 기존 CUDA 생태계(Linux 중심)와의 궤합이 관건이다. WSL 경유라면 오버헤드와 호환성 검증이 필요하다.

**시사점:** 'DGX Spark급 로컬 AI 박스'의 Windows판이 펼쳐지기 시작했다. llama.cpp·Ollama 생태계가 ARM 윈도우 하드웨어와 만나면 로컬 LLM의 주무대가 개발자 리눅스 박스에서 일반 데스크톱으로 넓어진다.
