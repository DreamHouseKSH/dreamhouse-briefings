## 1. SGLang, Triton 디코드 커널의 '조용한 오답' 수정 — 같은 모델이 GSM8K 50.87% vs 93.48%

- **원문:** https://mindpattern.ai/s/2026-11-15-inference-engines-are-trading-silent-wrong-answers-for-loud-failures-and-it-s-overdue · SGLang PR #47802
- **분야:** 엔진 · 정확성 버그
- **최초 게시:** MindPattern 2026-11-15, PR 머지 11-15
- **시간 판정:** 정규 구간 내 확인

### 요약

GLM-4-32B-0414 모델을 SGLang의 Triton 디코드 커널로 서빙하면 GSM8K(초등 수학 벤치마크) 점수가 50.87%에 그쳤지만, 같은 모델을 FlashAttention 3로 돌리면 93.48%였다 — 오류 메시지도 로그도 없이. 원인은 Triton grouped decode 커널이 GQA(Grouped Query Attention, 여러 쿼리 헤드가 KV 헤드를 공유하는 구조) 그룹이 16을 넘고 16의 배수가 아닌 경우를 잘못 처리한 것이다. 이 모델은 그룹이 24개라 헤드 24~31이 KV 헤드 0을 잘못 참조하고 있었다. 15일 머지된 PR #47802로 수정됐고, 수정 후 Triton에서도 93.48%를 기록했다. 특히 Hopper에서 fp8_e5m2 KV 캐시를 고르면 SGLang이 Triton 경로를 자동 선택하기 때문에, 메모리를 아끼려 작은 KV 캐시를 택한 사용자가 자기도 모르게 깨진 경로로 들어갈 수 있었다(fp8_e5m2 기준 49.51%→92.87%로 개선).

주의할 점도 있다. 93%와 51%의 격차는 단계별 풀이 프롬프트 기준이며, sgl-eval의 기본 boxed-answer 프롬프트에서는 모든 조합이 낮게 나온다(stock 30.02%, 수정 38.67%, FA3 38.51%). 수정으로 해당 커널이 약 1.35배 느려진다. 독립 검증자는 SM80 카드의 합성 커널 시험에서 헤드 매핑 오류를 재현했다(그룹 24에서 최대 절대 오차 2.25→수정 후 약 0.005)며 "서빙이나 GSM8K 주장은 아니다"라고 선을 그었다.

### 논조·다른 시각

- **기사 논조:** 비판적 경고 — "조용한 오답이 최악이며, 차라리 부팅을 거부하는 서버가 낫다"는 논조다.
- **논조 점검:** 버그와 수정은 PR과 독립 재현으로 확인됐지만, 특정 배포가 실제로 입은 피해는 프롬프트 방식에 따라 달라 일반화할 수 없다.
- **다른 시각:** SGLang의 1.0 릴리스 트래커(11-12 개시)는 '예측 가능한 설정'을 목표로 내걸었다 — 미지원 설정은 시작 시 거부하고 "설정을 조용히 바꾸거나 덮어쓰지 않는다. 남은 사례는 버그"라고 못 박았다. 0.5.x가 설정을 임의로 바꾸는 9개 사례가 열거돼 있다. 1.0이 나오면 0.5.x에서 잘 돌던 실행 스크립트가 실패할 수 있고, "그 실패가 기능"이라는 평가다.

**시사점:** attention 백엔드, KV 캐시 dtype, 양자화, 엔진 버전 중 하나라도 바꾸면 정확도 평가를 다시 돌려야 한다는 것이 실사례로 확인됐다. 시작 로그의 유효 설정과 실제 인자를 대조하는 습관이 필요하다.

## 2. vLLM, 같은 호스트 NIXL KV 전송 NVLink 복구 — AMD MI355X에는 SDMA 핸드오프 옵션 추가

- **원문:** https://repojournal.com/showcase/local-llm/week/2026-11-09/vllm-restores-nvlink-for-same-host-nixl-kv-transfer · vLLM PR #65658
- **분야:** 엔진 · 인퍼런스 성능
- **최초 게시:** RepoJournal 주간 리뷰 2026-11-15 (커버 범위 11-09~15), PR #65658 머지 11-15
- **시간 판정:** 정규 구간 내 확인(주간 리뷰·PR 기반)

### 요약

추론 엔진 vLLM에서 확장 KV 캐시(KV cache, 생성 중 중간 계산 결과를 저장해 재사용하는 메모리)가 기본값으로 전환된 뒤, 같은 호스트 안의 prefill(입력 처리)→decode(출력 생성) 간 KV 전송이 알게 모르게 고속 interconnect인 NVLink 대신 TCP로 우회하고 있던 문제가 수정됐다. NIXL(엔비디아의 노드 간 데이터 전송 라이브러리) 경로에서 IMEX 채널이 있으면 이제 FABRIC 핸들을 얻어 고대역폭 연결을 쓰고, IMEX가 없으면 NIXL은 기본 꺼짐으로 둔다. 즉 대역폭 회복 여부는 자기 호스트가 IMEX를 노출하는지 직접 확인해야 한다. ROCm 메모리 사이징과 sglang 일시정지 버그 수정도 같은 주에 보고됐다.

AMD 쪽에는 15일 머지된 PR #65658이 MI355X에서 파이프라인 병렬화를 위한 선택 옵션 --pp-sdma-handoff를 추가했다. ROCm에서 NCCL의 피어 복사가 blit 커널로 실행되며 보내는 쪽 GEMM이 411% 느려지던 것을, 복사를 SDMA 엔진으로 옮겨 1.4%로 줄였다. MiniMax-M3.1-Flash TP1×PP2 기준 prefill 처리량이 3.6% 늘고 평균 TTFT(첫 토큰까지 시간)가 3.4% 줄었다. 과정에서 "hipMemcpyAsync가 MI355X에서 피어 복사에 실패하면서도 성공(hipSuccess)을 반환해 런타임이 복사를 건너뛴다(HSA 상태 4097)"는 ROCm 런타임 문제가 문서화됐고, vLLM은 ROCr을 직접 호출해 우회한다. 이 기능은 PP2·TP1·gfx950·eager 모드·단일 노드 조건이 모두 맞지 않으면 초기화 단계에서 거부한다.

### 논조·다른 시각

- **기사 논조:** 해당 없음 — 주간 리뷰와 PR 기반의 정리다.
- **논조 점검:** 인간 검토를 거치는 주간지(RepoJournal)와 PR 문서 기반이다. 각 수정이 포함된 정식 릴리스 태그는 확인되지 않았다 — vLLM의 최신 태그는 여전히 v0.33.0 계열이다. ROCm 복사 이슈는 특정 HIP 7.16 이미지에서 관측된 런타임 동작이며 vLLM 버그가 아니다.
- **다른 시각:** P/D 분리(prefill과 decode를 나누는 서빙 구조)가 표준화되면서 '같은 호스트라도 고속 interconnect를 실제로 타는가'가 성능 변수로 부각됐다. "조건이 안 맞으면 시작을 거부"하는 설계는 1번 항목의 '조용한 실패보다 큰 실패' 흐름과 맞닿아 있다.

**시사점:** 분리형 서빙을 쓰는 팀은 vLLM 업데이트 후 같은 호스트 NIXL 경로가 실제로 NVLink를 타는지(IMEX 노출 여부) 점검하는 편이 좋다. ROCm에서는 디바이스 간 복사 결과를 한 번 읽어 보고 신뢰하라는 권고가 나온다.

## 3. llama.cpp, CUDA/Metal Top-K 샘플링의 결정성 수정 — FP8 KV 캐시 지원, 롤링 빌드 b12400대

- **원문:** https://repojournal.com/showcase/local-llm/week/2026-11-09/vllm-restores-nvlink-for-same-host-nixl-kv-transfer · https://github.com/ggml-org/llama.cpp/releases
- **분야:** 엔진 · 로컬 인퍼런스
- **최초 게시:** RepoJournal 2026-11-15, llama.cpp 릴리스 페이지(롤링)
- **시간 판정:** 정규 구간 내 확인(주간 리뷰·릴리스 페이지 기반)

### 요약

llama.cpp에서 CUDA/Metal의 radix Top-K 샘플링(확률 상위 k개 토큰 중 다음 토큰을 고르는 절차)이 정렬된 64비트 키 기반으로 재작성돼, 동점 점수의 토큰 선택이 실행할 때마다 동일하게 결정되도록 바뀌었다. 이전 경로의 스레드 타이밍 버그도 함께 고쳐졌다. 시드(seed)를 고정해 결과를 재현하는 실험에서 의미가 있는 수정이다. FP8 KV 캐시 지원 추가도 같은 주에 보고됐다. 정식 태그는 v1.0.1이 최신이며, 그 이후 변경은 롤링 사전판 빌드로만 배포된다 — 릴리스 페이지 기준 b12426까지 올라와 있다(관측 시점).

### 논조·다른 시각

- **기사 논조:** 해당 없음 — 주간 리뷰와 릴리스 페이지 기반의 정리다.
- **논조 점검:** 롤링 빌드는 사전판이며 개별 빌드의 안정성은 직접 검증이 필요하다. 결정성 수정은 CUDA/Metal 경로 기준이고 다른 백엔드까지 같은 보장을 하는지는 확인되지 않았다.
- **다른 시각:** 11-13의 v1.0.0 태그가 공개 C API의 호환성 약속(메이저 버전에서만 breaking change)을 정리했지만, 백엔드의 수치 동작 변경은 마이너·패치로 들어온다 — "버전 번호가 바인딩을 지켜줄 뿐 출력이 같다는 약속은 아니다"라는 MindPattern의 지적이 있다. 1번 항목과 같은 맥락에서 출력 검증은 사용자 몫이다.

**시사점:** 시드 기반 재현 실험의 신뢰도가 올라간다. 다만 v1.0 계열의 약속은 API 호환성이지 출력 동일성이 아니므로, 엔진 업데이트 후 회귀 평가를 습관화할 필요는 그대로다.
