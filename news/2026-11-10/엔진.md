### 요약

Ollama 0.40.16-rc0는 Qwen3.8 Flash Next를 애플 실리콘에서 실행할 때의 메모리 사용 방식을 조정하고, Claude Code를 실행할 때 선택한 제공자가 다른 설정에 가려지는 문제를 수정했다. RC(Release Candidate, 정식 배포 전 검증 후보)이므로 일반 안정판과 구분해야 한다.

Qwen 관련 수정은 모든 가중치를 가장 작은 형식으로 바꾸는 접근이 아니다. 개발자는 일괄적인 NVFP4(엔비디아의 4비트 부동소수점 표현) 적용이 긴 생성에서 품질을 해쳤다고 설명하고, 일부 계산은 BF16(16비트 부동소수점 표현)로 보존하면서 다른 적합한 가중치에는 MXFP8(미세 블록별 스케일을 쓰는 8비트 표현)을 사용했다. 또 매번 일부 행만 참조하는 큰 테이블을 파일에서 메모리 매핑해 필요한 행만 MLX(애플 실리콘용 머신러닝 계산 프레임워크)로 옮기도록 했다. 전체 테이블을 항상 장치 메모리에 올려놓지 않도록 하는 방식이다.

개발자가 제시한 모델 상주 메모리 수치는 97.6 GiB에서 70.8 GiB로 줄었다. GiB는 2의 거듭제곱 기준 용량 단위다. 이는 특정 모델·실행 조건에서 개발자가 보고한 수치이며 모든 작업의 전체 메모리나 속도를 보장하지 않는다. Claude Code 수정은 `ollama launch claude`가 Ollama 모델을 선택했는데도 상속된 제공자 설정 때문에 다른 경로를 사용하는 경우를 겨냥한다. 실행한 자식 프로세스에만 설정을 적용하고 사용자의 저장 설정과 명시적 출력·추론 설정은 보존하도록 했다.

### 논조·다른 시각

- **기사 논조:** 긍정. 대형 로컬 모델의 메모리 부담과 실행 설정의 예측 가능성을 개선한다.
- **논조 점검:** 메모리·속도 수치는 변경 작성자의 시험이며 독립 벤치마크가 아니다. 병합 날짜를 최초 릴리스 날짜로 바꾸어 쓰지 않았고, 특정 모델 최적화를 Ollama 전체의 속도 향상으로 일반화하지 않았다.
- **다른 시각:** 사용자는 출력 토큰을 생성하는 속도와 별개로 긴 입력을 처리하는 속도가 나쁘다고 지적했다. 개발자는 이후 장비별 입력 처리·생성 속도와 메모리 측정을 공개했다. 입력 처리와 출력 생성은 서로 다른 병목이므로 메모리 감소 하나만으로 체감 성능을 판단하기 어렵다. [사용자 의견](https://github.com/ollama/ollama/pull/18078#issuecomment-5724696039) · [후속 측정](https://github.com/ollama/ollama/pull/18078#issuecomment-5771181476)

**시사점:** 해당 모델을 메모리 용량이 제한된 Mac에서 쓰거나 Ollama와 Claude Code를 연결하는 사용자에게 의미가 있다. 안정판으로 간주하기보다 기존 모델의 답변 품질, 긴 입력 처리 시간, 실제 제공자 경로를 별도로 확인할 변화다.

- **사건·제공일:** 변경 제안 병합은 2026-11-09 13:10:12 UTC.

### 요약

llama.cpp의 b12229 사전 빌드는 서버 요청에서 문서에 안내된 JSON Schema(구조화 데이터의 필드·형식·조건을 지정하는 규칙)가 조용히 무시되는 경우를 수정했다. `response_format`의 형식을 `json_schema`로 지정하면서 `response_format.schema`에 직접 규칙을 넣으면 적용되지 않던 문제다. 규칙을 한 단계 더 감싼 `response_format.json_schema.schema` 방식은 이미 작동하고 있었다.

이번 수정은 직접 넣은 규칙도 읽도록 하되, 감싼 규칙이 함께 있으면 그쪽에 우선순위를 부여한다. 여기서 빈 객체인 `{}`도 유효한 규칙이므로, 내용이 비었는지가 아니라 해당 키가 존재하는지로 우선순위를 판단한다. 관련 시험과 문서도 함께 보강됐다. 단순히 문장이 보기 좋게 나오는 문제가 아니라, 결과를 다른 프로그램이 파싱하는 자동화에서 요구한 형식을 실제로 적용하는지에 관한 변경이다.

별도 참여자는 Debian 13의 CPU 환경과 Gemma 3 1B 모델에서, 수정 전 직접 지정 방식이 형식 지정 없는 요청과 같은 자유 형식 텍스트를 출력하고 수정 후에는 규칙을 따르는 사례를 재현했다. 다만 한 모델·환경의 재현이며 모든 스키마와 모델의 정확성을 입증하지는 않는다. 스키마 준수가 사실 정확성이나 업무 규칙 검증까지 대신하는 것도 아니다.

### 논조·다른 시각

- **기사 논조:** 긍정. 문서와 실제 동작의 불일치를 줄이고 구조화 출력 요청의 신뢰성을 높인다.
- **논조 점검:** 특정 요청 형태의 버그 수정이다. 기존의 모든 JSON 출력이 실패했다거나 모든 모델이 완벽한 구조화 출력을 보장한다고 확대하지 않았다.
- **다른 시각:** 별도 참여자의 재현은 문제의 범위를 구체화하지만 CPU·특정 모델에 한정된다. 검토 과정에서는 빈 스키마의 우선순위도 지적됐고, 작성자는 이에 맞춰 시험을 보강했다. 프로젝트 내 재현과 코드 검토이며 외부 서비스의 대규모 운영 검증은 아니다. [재현 결과](https://github.com/ggml-org/llama.cpp/pull/28697#issuecomment-5642014878) · [변경·검토 기록](https://github.com/ggml-org/llama.cpp/pull/28697)

**시사점:** llama-server를 구조화 데이터 추출이나 자동화에 사용하는 경우 실제 요청의 스키마 위치를 점검할 이유가 생겼다. 출력 파싱과 필수 필드 검증은 계속 별도로 유지해야 한다.

## 3. llama.cpp, Metal Flash Attention의 임시 메모리 범위 초과 수정

- **변경 제안:** https://github.com/ggml-org/llama.cpp/pull/31662

- **최초 게시:** 공식 릴리스 published_at 2026-11-09 12:28:21 UTC → **2026-11-09 21:28:21 KST**. prerelease=true.
- **시간 판정:** 정규 구간 내 배포 확인
- **사건·제공일:** 변경 제안 병합은 2026-11-09 11:32:28 UTC.

### 요약

llama.cpp b12221은 Metal(애플의 그래픽·범용 병렬 계산 기술)에서 Flash Attention(어텐션 계산의 메모리 이동을 줄이는 구현)을 실행할 때 특정 임시 메모리를 할당 범위 밖까지 초기화할 수 있는 문제를 수정했다. 벡터 계산 경로에서 SIMD(하나의 명령으로 여러 데이터를 병렬 처리하는 방식) 그룹의 모든 실행 단위가 초기화에 참여하면서, 일부 크기 조합에서는 허용 범위를 넘는 주소에 접근할 수 있었다.

수정은 유효한 실행 단위만 초기화하도록 조건을 추가한다. 개발자는 M2와 macOS 27.2의 특정 시험에서 셰이더 검증기가 보고한 범위 초과 오류가 109건에서 0건으로 줄었다고 제시했다. 이 결과는 해당 시험의 메모리 접근 오류를 확인한 것이며, 전체 모델의 속도 향상이나 모든 장치의 안정성을 측정한 자료는 아니다.

기존 아카이브의 대형 행렬 주소 계산 개선이나 전날의 Top-K 동점 처리와는 별개다. 이번에는 특정 Flash Attention 커널의 임시 공간 초기화 범위가 주제다. 공개 자료에 근거하지 않은 보안 취약점 등급이나 실제 공격 가능성은 부여하지 않았다.

### 논조·다른 시각

- **기사 논조:** 긍정. 계산 정확성과 안정성에 영향을 줄 수 있는 구체적인 메모리 접근 오류를 줄인다.
- **논조 점검:** 오류 수는 작성자의 장비·검증기 시험이다. 일반적인 충돌이 전부 해결됐다거나 별도 보안 취약점이 확인됐다고 표현하지 않았다.
- **다른 시각:** 시험 참여자는 관련 백엔드 시험은 통과했지만 전체 아키텍처 시험 중 별도의 Bus error가 있었다고 보고했다. 유지보수자는 이를 이번 수정과 무관한 문제로 판단했다. 이 의견은 분리해 기록하되 모든 시험이 완전히 정상이라는 뜻으로 바꾸지 않는다. [시험 결과와 별도 오류](https://github.com/ggml-org/llama.cpp/pull/31662#issuecomment-6726848361) · [유지보수자 판단](https://github.com/ggml-org/llama.cpp/pull/31662#issuecomment-6739006065)

**시사점:** 애플 실리콘에서 해당 계산 경로를 사용하는 사용자에게 의미 있는 안정성 수정이다. 실제 사용하는 모델·문맥 길이로 회귀 시험을 하고 별도 오류 여부도 함께 확인하는 것이 적절하다.
