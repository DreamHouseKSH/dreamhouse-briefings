## 1. llama-server, 깊게 중첩된 입력의 서버 중단 방어 강화

- **원문:** https://github.com/ggml-org/llama.cpp/releases/tag/b11871
- **분야:** IT · 공개 추론 서버 안정성·보안
- **날짜:** 2026-10-25 15:28 KST (릴리스 published_at 기준)

### 요약

llama.cpp b11871은 JSON(JavaScript Object Notation, 프로그램 사이에 구조화한 데이터를 주고받는 형식)이 128단계보다 깊게 중첩된 일부 요청을 미리 거부하도록 바꿨다. 개발자의 [변경 요청](https://github.com/ggml-org/llama.cpp/pull/30242)은 데이터 읽기 자체보다, 읽은 내용을 재귀적으로 처리하는 후속 코드에서 호출 스택이 소진되어 서버가 종료되는 문제를 설명한다.

적용 대상에는 도구 설명과 도구 호출 인수, 응답 형식, 일부 템플릿 설정 및 구조화 판단 요청이 포함된다. 한도를 넘으면 HTTP(Hypertext Transfer Protocol, 웹 요청과 응답의 통신 규칙) 400으로 거부한다. 이어 b11882에는 별도의 문법 파서에서 중첩 처리 깊이를 256으로 제한하는 [수정](https://github.com/ggml-org/llama.cpp/pull/29755)이 담겼다. 둘은 서로 다른 입력 처리 경로의 방어선이다.

다만 b11871의 작성자는 긴 참조 연결, 일부 템플릿 내부 처리, 미리 주어진 assistant 메시지 처리 등은 이 수정만으로 모두 해결되지 않는다고 명시했다. 이는 “입력으로 서버를 중단시킬 수 있는 모든 경우가 해소됐다”는 발표가 아니다. 개발자가 제시한 재현·시험 기록은 확인했지만, 이 브리핑이 별도로 공격을 실행하거나 운영 서버의 영향 여부를 확인한 것은 아니다.

### 논조·다른 시각

- **기사 논조:** 중립 — 문제의 발생 경로·차단 범위와 남는 한계를 함께 공개한 개발 기록이다.
- **논조 점검:** 특정 수정의 완료를 전체 안전성 보장으로 쓰지 않았다. 공식 취약점 번호·심각도 점수·실제 피해 발생은 이 기록만으로 확인되지 않는다.
- **다른 시각:** [같은 수정의 미해결 범위](https://github.com/ggml-org/llama.cpp/pull/30242)는 일부 템플릿이 128보다 낮은 깊이에서도 실패할 수 있음을 밝힌다. 독립 반론을 찾지 못했으므로, 이를 외부 전문가 평가가 아니라 작성자가 공개한 제한으로 구분한다.

**시사점:** 외부 입력을 받는 추론 서버에서는 모델 답변 품질뿐 아니라 요청 크기와 구조를 다루는 코드도 운영 안정성의 일부다. 버전 확인은 필요하지만 이 변경 하나를 전체 보안 점검의 대체물로 볼 수 없다.

## 2. 반복 억제 설정의 중복 처리로 발생하는 자원 낭비 수정

- **원문:** https://github.com/ggml-org/llama.cpp/releases/tag/b11884
- **분야:** IT · 추론 서비스 자원 관리
- **날짜:** 2026-10-26 02:55 KST (릴리스 published_at 기준)

### 요약

llama.cpp b11884는 반복 생성을 억제하는 설정인 `dry_sequence_breakers`에 많은 항목이 들어갔을 때 초기화에 과도한 연산과 메모리가 드는 문제를 수정했다. [변경 설명](https://github.com/ggml-org/llama.cpp/pull/31035)에 따르면 중복 검사가 불완전했고, 같은 단어 목록을 반복해서 복원하거나 동일한 부분 문자열을 여러 번 처리하는 낭비가 있었다.

수정은 중복 항목을 먼저 제거하고 개수를 제한하며, 반복되는 계산을 재사용하도록 바꾼다. 웹 요청에서 한도를 초과하면 오류 응답을 돌려주고, 내부 처리 경로에서는 잘라내기와 경고를 사용한다고 작성자가 설명했다. 단순히 더 빠른 모델이 나온 소식이 아니라, 설정 입력이 자원 소모로 이어지는 경로를 줄인 작업이다.

작성자는 Linux의 특정 소형 모델 조건에서 전후 측정과 시험을 제시했다. 여기서는 그 결과를 모든 모델의 응답 지연이나 처리량 향상으로 옮겨 쓰지 않았다. 실제 서비스의 영향은 해당 설정 사용 여부와 요청을 누가 제어할 수 있는지에 따라 달라지며, 운영 환경의 피해 발생은 확인하지 않았다.

### 논조·다른 시각

- **기사 논조:** 긍정 — 불필요한 반복 계산과 자원 낭비를 줄인 결과를 제시한다.
- **논조 점검:** 성능·정상 작동의 근거는 수정 작성자의 특정 시험 환경이다. 일반적인 추론 가속 수치로 확대하지 않았다.
- **다른 시각:** 찾은 반론 없음 (검색 범위: 공식 릴리스와 연결된 변경 요청). 예상 쟁점: 제한 도입은 비정상 입력을 줄이지만 많은 설정 항목을 사용하던 호출자는 오류 응답 처리도 확인할 필요가 있다.

**시사점:** 생성 설정도 검증해야 할 외부 입력이다. 중복 제거와 입력 제한은 모델 교체 없이도 자원 소모 경로를 줄일 수 있다.

## 3. tuios 0.11.0, 다른 에이전트의 승인창에 답할 수 있던 권한 우회 수정

- **원문:** https://github.com/Gaurav-Gosain/tuios/releases/tag/v0.11.0
- **보안 공지:** https://github.com/Gaurav-Gosain/tuios/security/advisories/GHSA-78rj-pghh-vh42
- **분야:** IT · 에이전트 관리 도구 보안
- **날짜:** 2026-10-25 20:40 KST (릴리스 published_at 기준)

### 요약

터미널 안에서 여러 작업 화면과 에이전트를 관리하는 tuios가 0.11.0에서 권한 우회를 수정했다고 공개했다. 공식 보안 공지는 0.10.1 이하를 영향 버전으로, 0.11.0을 수정 버전으로 표시하며 심각도를 중간으로 분류한다.

문제는 한 작업 화면의 프로세스가 다른 에이전트의 상태를 바꾼 뒤, 사람의 승인을 기다리는 창에 답할 수 있었던 것이다. 공식 설명은 외부 지시에 속은 에이전트도 같은 상주 서버에 연결된 다른 에이전트의 승인 경계를 넘을 수 있었다고 밝힌다. 수정 후에는 다른 화면의 상태를 보고·변경하는 경로에도 별도 권한을 검사한다.

릴리스는 새 프로그램 파일을 설치하는 것만으로 충분하지 않고 상주 서버도 새 버전으로 다시 시작해야 보안 수정이 적용된다고 안내한다. 다시 시작할 때 실행 중인 프로그램의 중단·복원 안내와 확인 과정이 있으므로 작업 상태를 보존하는 절차가 중요하다. 이 브리핑에서는 설치나 재시작을 수행하지 않았다.

### 논조·다른 시각

- **기사 논조:** 혼재 — 새 기능을 홍보하면서 승인 경계의 결함과 수정 필요성을 공개한다.
- **논조 점검:** 공식 공지는 영향 조건과 수정 버전을 제시하지만 실제 악용 피해를 확인한 보고는 아니다. 사용자가 해당 도구를 사용 중이라고 추정하지 않는다.
- **다른 시각:** 독립 반론은 찾지 못했다 (검색 범위: 릴리스와 보안 공지). [업그레이드 안내](https://github.com/Gaurav-Gosain/tuios/releases/tag/v0.11.0#upgrading)는 실행 중인 상주 서버 갱신을 별도로 요구한다. 버전 파일만 바뀌었다는 확인으로 수정 적용을 단정하면 안 된다.

**시사점:** 에이전트의 승인창은 다른 에이전트가 대신 넘을 수 없어야 한다. 여러 에이전트를 한 도구에서 관리할수록 화면 사이의 권한 분리가 중요하다.
